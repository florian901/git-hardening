# Injecting 1Password Secrets into EC2 Under Zero-Plaintext-at-Rest: Architecture Comparison, Threat Model, and Ranked Recommendation

## TL;DR
- **For interactive provisioning, use time-boxed, per-connection 1Password SSH agent forwarding (Architecture A) as your "split-ssh," transported over an AWS SSM Session Manager tunnel (no inbound ports), and treat 1Password's per-use biometric prompt — not OpenSSH destination constraints — as your only hijack control.** The load-bearing fact: 1Password's SSH agent does **not** implement `session-bind@openssh.com` or `restrict-destination-v00@openssh.com`, so OpenSSH 8.9+ destination-constrained forwarding is unavailable with it (confirmed by the `ssh_agent_bind_hostkey: agent refused operation` signature across 1Password 8.10.x / OpenSSH 9.0).
- **For unattended app runtime secrets, deliver each secret once over the provisioning SSH channel and seal it with `systemd-creds encrypt` bound to NitroTPM 2.0, consumed via `LoadCredentialEncrypted=`/`SetCredentialEncrypted=`** into a ramfs-backed, non-swappable `$CREDENTIALS_DIRECTORY`. This is the only option that satisfies zero-plaintext-at-rest AND keeps minting authority on the laptop. NitroTPM requires a UEFI + `--tpm-support v2.0` AMI; it is **not** on by default for typical Linux AMIs.
- **Disqualify: secrets in user-data/AMIs/EBS; a long-lived 1Password Service Account token or signed-in `op` on the instance; unrestricted/persistent `ForwardAgent yes` in a `ControlPersist` master; and AWS Secrets Manager + instance IAM role as the *primary* path (it moves minting authority to the instance, violating constraint 2).**

## Key Findings

1. **1Password's SSH agent lacks OpenSSH destination-constraint support (the single most important fact).** OpenSSH 8.9 (released 2022-02-23) introduced destination-constrained agent forwarding via three protocol extensions documented in `PROTOCOL.agent`: the key-constraint extension `restrict-destination-v00@openssh.com` (`SSH_AGENT_CONSTRAIN_EXTENSION 0xff`), the session-binding extension `session-bind@openssh.com`, and the `publickey-hostbound@openssh.com` authentication method. 1Password's agent refuses the session-bind request: OpenSSH logs `get_agent_identities: ssh_agent_bind_hostkey: agent refused operation` and then proceeds to return keys — the canonical fingerprint of an agent that does not implement session binding. Because destination constraints are cryptographically dependent on session binding, `ssh-add -h`/`RestrictDestination` cannot be enforced with 1Password. Confidence: **high** for session-bind absence (diagnostic error signature reproduced across 1Password 8.10.33 on macOS 14.5 and other 8.10.x builds, OpenSSH 9.0p1), **moderate-high** for destination-constraint absence (inferred from the session-bind dependency plus total documentation silence).

2. **1Password substitutes its own per-use approval model for destination constraints.** Per 1Password's forwarding docs, unlike stock OpenSSH ssh-agent (where every key is usable on the remote host with no further auth), the 1Password agent fires a biometric/desktop approval prompt for each *key* the first time it is used from a forwarded session — "making agent forwarding more secure with 1Password than with the OpenSSH agent." But 1Password's docs explicitly warn: "If you approve the request, the entire IDE will be authorized to use that key. Any process running on the cloud development environment under the same OS user will also be authorized, which is a security consideration to keep in mind." Approval authorizes the OS-user session, not a single signing operation, and the prompt shows the *key/app*, **not the destination host** of the forwarded request.

3. **OpenSSH's own design says destination constraints do not stop a hijacker on the compromised hop anyway.** Verbatim from openssh.org/agent-restrict.html: "If an agent is forwarded to an attacker-controlled host, then they will still be able to steal use of a forwarded agent on that host… they will also be able to forward use of the agent to other hosts, e.g. by using an SSH implementation that doesn't cooperate with ssh-agent, or another tool entirely, such as socat." Constraints limit *where* a key works, not whether root-on-the-hop can use it while forwarded. So the loss from 1Password's missing support is real but bounded: you lose "this key only works to host X," you do not lose a defense against local hijack (which never existed for a forwarded socket).

4. **NitroTPM 2.0 + systemd-creds is a genuine zero-plaintext sealing path, with caveats.** NitroTPM is a TPM 2.0-compliant virtual device on Nitro-based instances that support UEFI boot. Per the AWS News Blog: "we support all Intel and AMD instance types that support UEFI boot mode. Graviton1, Graviton2, Xen-based, Mac, and bare-metal instances are not supported." (Newer Graviton families such as M8g/R8g now appear in the current NitroTPM prerequisites instance list.) It is **not enabled by default** for typical Linux AMIs — you must register the AMI with `--boot-mode uefi --tpm-support v2.0` (AWS provides some Windows AMIs pre-configured). `systemd-creds encrypt` can seal to the TPM2 (default binds to PCR 7), and the systemd-creds(1) man page confirms decrypted credentials in the "secure" state are "backed by unswappable memory, i.e. 'ramfs'." AWS announced **GA of EC2 instance attestation on 2025-09-23**: "AWS announces the general availability of EC2 instance attestation… powered by Nitro Trusted Platform Module (NitroTPM) and Attestable Amazon Machine Images (AMIs)… available in all AWS Commercial Regions, including the AWS GovCloud (US) Regions," integrating with KMS to gate key operations on attestation state.

5. **`op` CLI cannot be safely "run remotely" against the desktop app; only the SSH-agent socket and the *authorization* can cross the network.** The `op` CLI's biometric/desktop integration uses a local per-user IPC channel — "XPC via the 1Password Browser Helper on macOS, a Unix domain socket on Linux, a named pipe on Windows" — whose authenticity is verified by code-signature (Authenticode/Developer ID); it is not a network protocol. Community tools such as `op-forward` work only by running an `op` shim on the remote that tunnels each invocation back to a **loopback-bound (127.0.0.1)** daemon on the laptop over SSH RemoteForward, keeping Touch ID on the laptop. This forwards the *authorization*, not remote execution against the vault.

6. **A mid-2026 CVE shows how fragile forwarded constraints are even in compliant stacks.** CVE-2026-39832 (Go `x/crypto/ssh/agent`, issue #79435, opened 2026-05-16; GO-2026-5006; CVSS v3.1 9.1 Critical; fixed in golang.org/x/crypto v0.52.0; reported by "NCC Group Cryptography Services, sponsored by Teleport"): "When adding a key to a remote agent constraint extensions such as restrict-destination-v00@openssh.com were not serialized in the request. Destination restrictions were silently stripped when forwarding keys, allowing unrestricted use of the key on the remote host." Relevant because many "proxy agent" shims are built on Go's library — re-check any such shim before relying on forwarded constraints.

## Details

### Primary-source version/timeline anchors
- **OpenSSH 8.9 (2022-02-23):** introduced agent restriction (`ssh-add -h`, destination constraints). Extensions in `PROTOCOL.agent`: `restrict-destination-v00@openssh.com`, session-bind, and `publickey-hostbound@openssh.com`.
- **CVE-2023-28531 (fixed 9.3p1):** smartcard keys added with `ssh-add -h` had constraints silently dropped (a logic error prevented constraints reaching the agent).
- **CVE-2023-38408 (fixed 9.3p2, 2023-07-19):** PKCS#11 RCE via a forwarded agent socket — reinforces "don't forward agents to untrusted hosts."
- **Fixed 9.6 (advisory 2023-12-18):** destination constraints were applied to only the first PKCS#11 key returned from a token.
- **OpenSSH 10.0p2 (seen in openSUSE 16.0):** ssh-agent refuses remote PKCS#11 module loads by default (`-Oallow-remote-pkcs11` to restore); note "ssh-agent depends on the SSH client to identify requests that are remote… forwarding access to an agent socket using other tools may circumvent this restriction." Later 9.9→10.x releases also fixed `DisableForwarding` failing to disable agent/X11 forwarding.
- **Fail-safe property (agent-restrict.html):** if an agent lacks destination-constraint support, `ssh-add` of a constrained key *fails* (constraints are treated as critical); a forwarded connection presenting an unbound auth request is refused. This is why 1Password's lack matters — you cannot "add with constraints" and have it silently work.

### Architecture A — 1Password SSH agent forwarding
**Mechanics:** The 1Password 8 desktop app provides the agent socket at `~/.1password/agent.sock` (Linux) or `~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock` (macOS). `ForwardAgent yes` (or `ssh -A`) exposes a proxy socket on the instance (`$SSH_AUTH_SOCK` → `/tmp/ssh-XXXX/agent.<pid>`); signing requests travel back to the laptop, where 1Password prompts for approval. Private keys never leave the vault.

**What touches disk where:** On the instance, only a Unix-domain socket in `/tmp` owned by your OS user; no key material. On the laptop, keys are encrypted in the vault. Nothing in AMI/user-data/EBS.

**What root-on-instance gains:** While your forwarded socket exists, root can connect to it (Unix socket perms do not stop root) and request signatures. With 1Password, the *first* use of a given key raises a laptop prompt — but the prompt shows the key/app, not the destination, and once approved it authorizes all processes under your OS user for the session. A root attacker acting *during* your provisioning window, using the *key you just approved*, can obtain signatures without a fresh distinguishable prompt. They cannot extract the key; they cannot use it after your session ends and the socket is gone.

**Destination constraints:** Unavailable (Finding 1).

**Maturity/friction:** Very mature, low-friction, widely used with VS Code Remote-SSH. Known interop gaps: JetBrains Gateway agent-forwarding bug (YouTrack IJPL-328); recurrent `MaxAuthTries`/six-key exhaustion, mitigated via `~/.config/1Password/ssh/agent.toml` key ordering and per-host `IdentityAgent`.

### Architecture B — Reverse-forwarding the op socket / named pipes
**Mechanics:** `RemoteForward /run/user/1000/op-agent.sock ~/…/agent.sock` (for RemoteForward the *first* path is remote, the second local) or socat/ncat bridges. Requires `StreamLocalBindUnlink yes` in the **remote** sshd_config to clear stale sockets (a client-side setting does not clean the remote socket).

**Three channels to distinguish (the crux of B):**
1. **The SSH agent socket** — safe to forward across the network in the same sense as A (only signatures cross; keys stay in vault). This is "1Password SSH-agent forwarding."
2. **The `op` CLI ↔ desktop-app IPC channel** — a *local-only*, code-signature-verified XPC/named-pipe/UDS. Not a network protocol; cannot be safely exposed raw to a remote host.
3. **CLI *session* forwarding** — done correctly only by running an `op` shim remotely that tunnels each invocation back to a **loopback-bound** daemon on the laptop (e.g., `op-forward`: binds 127.0.0.1 only, 32-byte bearer token with 0600 perms and 30-day sliding expiry, blocks `signin/signout/update/completion`, rejects shell metacharacters, Touch ID per privileged op). Keeps authorization on the laptop.

**Security delta vs A:** RemoteForward of a Unix socket lets you set socket ownership/mode via `StreamLocalBindMask` (default umask `0177` → owner-only), but **root still bypasses socket perms**, and there are no `PermitOpen`/`PermitListen` equivalents for Unix sockets — you cannot restrict the remote socket path server-side. Net: no better than A against root; more moving parts.

### Architecture C — Qubes-style split-ssh for the cloud
**Qubes baseline:** split-ssh uses qrexec RPC where the vault VM holds keys and prompts per request; only signatures cross the boundary; policy in `/etc/qubes-rpc/policy/qubes.SshAgent` (e.g., `@anyvm @anyvm ask,default_target=vault`) gates which client VM may request. Crucially, Qubes' own docs warn the prompt "won't see what was requested," and community guides note "a malicious ssh-client AppVM can hold onto the ssh-agent connection for more than one use until it is shut down." Even the gold-standard split model gives neither content-aware per-op approval nor protection against hold-open hijack.

**Closest laptop→EC2 equivalents:**
- **(i) Plain agent forwarding *is* essentially split-ssh** minus qrexec's policy engine. Delta: qrexec adds a per-*request* prompt naming the *source domain*; 1Password's prompt names the *key/app*, not the destination. Neither prevents socket impersonation by a compromised hop. 1Password's per-key approval is arguably stronger than Qubes' default (which "won't see what was requested" and can be set to auto-accept for minutes/a day via `QUBES_GPG_AUTOACCEPT`).
- **(ii) Brokered signers:** `ssh-tpm-agent` (Foxboron; Arch package v0.9.0 in 2026) seals keys to a TPM with PIN and TPM dictionary-attack protection and supports remotely-wrapped keys — but the TPM is the laptop's or the instance's, and keys live in the TPM, not the 1Password vault, so it does not compose with 1Password. Sigstore-style keyless signing is for artifact signing, not interactive SSH auth. A bespoke gRPC/SSH-RPC signer with per-op approval is buildable but unproven.
- **(iii) Hardware anchors:** FIDO2 `-sk` resident keys with `verify-required` and YubiKey touch-per-op give genuine per-operation user-presence — OpenSSH's design notes call these "a little more defence" though "similarly phishable." **1Password does not store/serve FIDO2 `-sk` SSH keys through its agent, nor SSH certificates**, so these do not compose with 1Password today (you can pair a vault key with an on-disk `CertificateFile`, per a 2024 community thread, but 1Password "does not support certificates in… the ssh agent").
- **Production-credible remote split-ssh with per-op local approval that composes with 1Password:** none. Closest are Qubes split-ssh (not cloud) and `op-forward` (community, single-maintainer). Mark as a gap.

### Architecture D — Push/pull injection for env + provisioning secrets
- **(i) Pull with local authorization:** Laptop runs `op run --env-file` / `op inject` and streams to a one-shot process over the SSH channel via stdin. **Avoid `SendEnv`/`SetEnv`** — values land in `/proc/<pid>/environ` and `ps`, are root-readable, and sshd must be configured to accept them. systemd's own credentials rationale states the framework exists to "move away from environment variables or command-line arguments for secret passing, which can be leaked via /proc."
- **(ii) systemd credentials sealed to NitroTPM (recommended runtime path):** Deliver a secret once over SSH, `systemd-creds encrypt` to ciphertext, embed as `SetCredentialEncrypted=` in a (world-readable) unit — safe because "the ciphertext… cannot be decoded unless access to TPM2/encryption key is available" — or reference via `LoadCredentialEncrypted=`. Decrypted creds land in the ramfs, non-swappable `$CREDENTIALS_DIRECTORY`, service-only. Caveat: the default TPM+host mode ("the default mode of operation if a TPM2 chip is available and /var/lib/systemd/ resides on persistent media") stores half the key in `/var/lib/systemd/credential.secret` on disk; Smallstep warns "an attacker could install the same bootloader and OS kernel on another volume on your machine, and gain access to the TPM key." For snapshot-proof sealing, bind to TPM only (`--with-key=tpm2`, or `auto-initrd` for generators) plus Secure Boot / measured boot (PCR 7). A systemd maintainer confirmed there is no "host key in RAM" mode (issue #23566).
- **(iii) Connect / Service Accounts / `op` on the instance:** A Service Account token (`OP_SERVICE_ACCOUNT_TOKEN`) is a **long-lived plaintext credential that can mint more secrets** — directly violating constraints 1 and 2 if placed on the instance. 1Password's docs: "Treat this token like a password, and don't store it in plaintext." It can be confined (memory-only via `LoadCredentialEncrypted`, IMDSv2-gated retrieval, KMS-wrapped) but confinement does not remove the instance's autonomous minting ability → **disqualified as primary**; acceptable only for genuinely unattended workloads, TPM-sealed + tightly vault-scoped + short `--expires-in`. 1Password's newer **Credential Broker** (2025) uses platform-issued OIDC-style identity instead of a standing token ("no credential to distribute, store, or rotate, and the workload never receives standing access to the vault") — philosophically better but AWS-workload/OIDC-oriented, not laptop-anchored.
- **(iv) AWS-native hybrid:** Laptop uses 1Password Shell Plugins for short-lived AWS creds, then Secrets Manager / SSM Parameter Store + instance IAM role at runtime. **Honest accounting:** trust moves to the *instance role* — root reads IMDS (`169.254.169.254`) and assumes the role, minting at will (violating constraint 2). Lost vs the sealed-creds path: laptop-anchored authorization, per-secret human approval, "instance can't mint more." Gained: rotation, simplicity, CloudTrail audit. **SSM Session Manager port-forwarding beats plain SSH for transport** (no inbound ports; instance in private subnet, outbound-only to SSM endpoints; IAM-authorized; CloudTrail-audited) and should be used regardless — but SSM as a *secrets* mechanism still rests on the instance role.
- **(v) EC2 Instance Connect & SSH certs:** Per the AWS EC2 User Guide, "the EC2 Instance Connect API automatically pushes an SSH public key to the instance metadata where it remains for 60 seconds. An IAM policy attached to your user authorizes this action." Excellent for eliminating long-lived `authorized_keys`; use EIC Endpoint (EICE) for private instances. Caveat: EIC + IMDS is itself a documented attacker pivot to steal instance-profile creds (HackTricks), underscoring constraint-2 discipline. SSH CAs (step-ca, or a CA key "in 1Password") issue short-lived certs — but 1Password's agent cannot sign certificates, and destination-restricted keys cannot do CA/signature ops per OpenSSH, so a CA key "in 1Password" implies extraction at signing time, weakening the boundary.

### Architecture E — Socket-hijacking mitigations (cross-cutting)

| Control | What it does | vs non-root | vs root | vs EBS snapshot |
|---|---|---|---|---|
| Ephemeral socket path (`/tmp/ssh-XXXX`) | Limits socket lifetime/discoverability | Yes | No (root reads `/proc/*/environ` for `SSH_AUTH_SOCK`) | N/A |
| `StreamLocalBindUnlink yes` + `StreamLocalBindMask 0177` | Clean stale sockets; owner-only mode | Yes | No | N/A |
| Socket dir perms `0700` | Blocks other users | Yes | No | N/A |
| `ExitOnForwardFailure yes` | Fail closed if forward can't bind | integrity | integrity | N/A |
| Time-boxing (no `ControlPersist`/long `ControlMaster`) | Shrinks hijack window to active session | Yes | **Primary control** vs root | N/A |
| 1Password per-use approval | Prompts on first key use; session/app-scoped | Yes (friction) | Partial — can't distinguish attacker during window; no destination shown | N/A |
| `ssh-add -c` (stock agent) | Per-signature confirmation | Yes | Partial (OpenSSH: confirmation "somewhat easy to phish") | N/A |
| Destination constraints (`ssh-add -h`) | Key only works to listed hosts/paths | Bounds blast radius | Does **not** stop local hijack (socat bypass) | N/A |
| Encrypted EBS + no swap + ramfs creds | No plaintext to snapshot | N/A | N/A | **Primary control** |

**Which agents implement `restrict-destination-v00@openssh.com`:** OpenSSH `ssh-agent` (yes, native); gpg-agent (partial/varies); **1Password (no)**; **Bitwarden (no** — comparable requests open); **KeePassXC (no** — open issue #9801); Strongbox (no — issue #772); `ssh-tpm-agent` (not documented). Only stock OpenSSH ssh-agent robustly supports it. **Auditing:** stock ssh-agent + constraints logs signing; 1Password logs approvals in the desktop app / Business audit events (per-key, not per-destination); SSM/EIC give CloudTrail with requester IAM identity — the strongest audit trail available here.

## Recommendations

### (a) Interactive provisioning — PRIMARY: time-boxed 1Password agent forwarding over an SSM tunnel
Rationale: keys stay in the vault; 1Password's per-key biometric prompt is your approval gate (accept it is session-scoped, not per-op/per-destination); SSM removes inbound ports and gives IAM+CloudTrail audit; **time-boxing is the real hijack control** since destination constraints are unavailable.

Stage 1 — transport (no inbound SSH port; instance private, no public IP):
```
# ~/.ssh/config
Host prov-*
  User ec2-user
  ProxyCommand sh -c "aws ssm start-session --target %h --document-name AWS-StartSSHSession --parameters portNumber=%p"
  IdentityAgent "~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock"
  ForwardAgent yes          # ONLY for provisioning hosts
  ControlMaster no          # never persist a shared, hijackable socket
  ControlPersist no
  ExitOnForwardFailure yes
```
Get short-lived AWS creds from 1Password first (Shell Plugin), so no long-lived AWS keys on disk: `op plugin run -- aws ssm start-session …`.

Stage 2 — prefer a short-lived *login* credential so there is no long-lived `authorized_keys`:
```
ssh-keygen -t ed25519 -f /tmp/eic -N ''
aws ec2-instance-connect send-ssh-public-key --instance-id i-0abc123 \
  --instance-os-user ec2-user --ssh-public-key file:///tmp/eic.pub   # valid 60s
ssh prov-i-0abc123    # do the work; 1Password prompts on first key use; socket dies with the session
```

**Thresholds that change this:** If you require cryptographic "this key only to host X" enforcement or per-operation approval, move off 1Password's agent to stock `ssh-agent` + `ssh-add -h` (losing vault integration) or FIDO2 `-sk` keys with touch-per-op (losing 1Password). If root cannot be trusted during the window, do not forward the agent at all — use SSM shell + sealed creds only.

### (b) Unattended app runtime secrets — PRIMARY: deliver-once over SSH, seal to NitroTPM via systemd-creds
Prereq — launch on a NitroTPM AMI:
```
aws ec2 register-image --name my-app --boot-mode uefi --architecture x86_64 \
  --root-device-name /dev/xvda \
  --block-device-mappings 'DeviceName=/dev/xvda,Ebs={SnapshotId=snap-...}' \
  --tpm-support v2.0
# verify: aws ec2 describe-images --image-id ami-... → "TpmSupport":"v2.0","BootMode":"uefi"
# runtime: systemd-creds has-tpm2  → yes
```
Deliver + seal in one shot from the laptop (plaintext never hits instance disk):
```
op read "op://Prod/db/password" \
  | ssh prov-i-0abc123 \
    'systemd-creds encrypt --name=db-password --with-key=tpm2 - /etc/credstore.encrypted/db-password.cred'
```
Consume in the service (decrypted only into ramfs `$CREDENTIALS_DIRECTORY`, service-only):
```
# /etc/systemd/system/myapp.service
[Service]
LoadCredentialEncrypted=db-password:/etc/credstore.encrypted/db-password.cred
ExecStart=/usr/bin/myapp        # reads $CREDENTIALS_DIRECTORY/db-password (NOT an env var)
MemorySwapMax=0
PrivateTmp=yes
ProtectSystem=strict
```
For whole `.env` files, render with `op inject`/`op run --env-file` on the laptop, seal the composite, and have the app read files from `$CREDENTIALS_DIRECTORY` (avoids `/proc/<pid>/environ`).

**Thresholds that change this:** No NitroTPM (Graviton1/2, bare-metal, Mac) → fall back to `--with-key=host` on an **encrypted EBS volume with swap disabled**, accepting that root with the running host key can decrypt (still snapshot-resistant if `/var` is encrypted). If you truly need unattended minting (no laptop in loop), only then introduce a **tightly-scoped, short-`--expires-in` Service Account token delivered as a TPM-sealed systemd credential** — and document that you have accepted a constraint-2 relaxation.

### Ordering summary
1. **A over SSM (interactive)** + **D-ii NitroTPM sealed creds (runtime)** — recommended pairing.
2. **E controls always on:** no `ControlPersist`; `ExitOnForwardFailure yes`; forward only to provisioning hosts; EIC/short-lived login creds; SSM for transport.
3. **C-iii FIDO2/`-sk` or stock ssh-agent + `ssh-add -h`** only if you must have per-op/destination enforcement and will drop 1Password vault integration for SSH auth.
4. **B (`op-forward`-style)** only when you need the `op` CLI itself remotely with laptop biometrics; niche.

## Disqualified approaches
- **Secrets in EC2 user-data / baked into AMIs / on EBS / in shell history / in swap** — violates constraint 1; user-data is readable via IMDS by any instance process.
- **Long-lived 1Password Service Account token (or signed-in `op`) resident on the instance** — violates constraints 1 & 2 (plaintext, self-minting; 1Password says don't store in plaintext). Acceptable only fully-confined + TPM-sealed for unattended workloads.
- **`SetEnv`/`SendEnv` to pass secrets over SSH** — lands in `/proc/<pid>/environ`, `ps`, root-readable.
- **Unrestricted `ForwardAgent yes` for `Host *`, or agent forwarding inside a `ControlPersist` master** — violates constraint 4: a long-lived hijackable socket usable by root for its lifetime.
- **Secrets Manager / SSM Parameter Store + instance IAM role as the *primary* secrets path** — violates constraint 2 (IMDS → assume role). Fine as *transport* (SSM Session Manager) and as a runtime *fallback* store, not as the trust root.
- **"CA key in 1Password" for SSH certificates** — 1Password's agent cannot sign certificates and destination-restricted keys can't do CA/signature ops (OpenSSH); requires extracting the CA key at signing time.

## Open questions / gaps (tooling that does not exist yet)
- **1Password destination-constraint / session-bind support:** Not implemented as of 1Password 8.10.x (mid-2026). No official statement either way; conclusion rests on the `ssh_agent_bind_hostkey: agent refused operation` signature (reproduced across builds/dates) and documentation silence. Related feature requests exist ("Feature Request: SSH Agent improvements"; host-to-key mapping thread #170418) but none tracks session-bind/`restrict-destination`. **Confidence: high (session-bind), moderate-high (destination constraints).** This is the single fact most likely to change the recommendation if 1Password ships it.
- **Per-operation (not per-session) approval in 1Password's agent:** does not exist; no configurable "confirm every signature" akin to `ssh-add -c`.
- **1Password + FIDO2 `-sk` keys and SSH certificates:** unsupported in the agent; blocks the strongest per-op hardware-presence and short-lived-cert designs from composing with the vault.
- **Production-credible remote split-ssh with per-op local approval integrating with 1Password:** none. `op-forward` (single-maintainer) is the closest for CLI.
- **systemd-creds "host key in RAM" mode:** requested (systemd #23566), not implemented — non-TPM instances can't get a purely volatile master key without hacks.
- **Go `x/crypto` constraint-stripping (CVE-2026-39832, CVSS 9.1):** fixed in x/crypto v0.52.0; audit any proxy-agent shim built on Go's library before relying on forwarded constraints.
